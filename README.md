# FileCollector

Потокобезопасная сборка файлов из чанков. Чанки приходят в произвольном порядке, могут пересекаться и повторяться, один файл может собираться несколькими потоками одновременно. В комплекте визуализатор на Dear ImGui, который показывает процесс сборки.

## Визуализатор

```bash
cmake -S . -B build -DFC_BUILD_VISUALIZER=ON
cmake --build build -j
./build/visualizer/fc_visualizer [config.ini]
```

Визуализатор загружает файл с диска и передаёт его в коллектор чанками из нескольких потоков. Поддерживаются два режима:

- `Stable`: крупные чанки примерно по порядку, используется `IntervalTracker`.
- `Unstable`: мелкие чанки в случайном порядке, с пересечениями и дубликатами, используется `BitmapTracker`.

  <img width="2532" height="1464" alt="image" src="https://github.com/user-attachments/assets/f3a178c0-80d3-45e0-b960-606b98c0de47" />


Файл отображается сеткой ячеек, количество ячеек настраивается и не зависит от количества чанков. Цвет ячейки меняется от серого к зелёному пропорционально доле полученных байт. После остановки передачи неполученные данные отображаются красным. Выбор ячейки заполняет диапазон для просмотра; окно просмотра показывает долю полученных данных и hex-дамп, в котором отсутствующие байты обозначены `??`. После завершения передачи файл извлекается через `TakeFile` и сравнивается с исходным.

Параметры задаются в `visualizer/config.ini`: число потоков, длительность передачи, размеры чанков, ограничения на размер файла и диапазона просмотра. По умолчанию используется файл из каталога исходников, изменения применяются без пересборки.

Путь к файлу проверяется при открытии: пустой путь, отсутствующий файл, каталог, пустой файл, превышение лимита размера и отсутствие прав на чтение приводят к сообщению об ошибке.

## Сборка

Требования: компилятор с поддержкой C++20, CMake 3.20+, git. GoogleTest, GLFW и Dear ImGui загружаются через FetchContent.

```bash
cmake -S . -B build
cmake --build build -j
ctest --test-dir build
```

| Опция | Значения | По умолчанию | Описание |
|---|---|---|---|
| `FC_TRACKER` | `intervals`, `bitmap` | `intervals` | Трекер, используемый в `fc::FileCollector` |
| `FC_SANITIZER` | `none`, `thread`, `address` | `none` | `address` также включает UBSan |
| `FC_BUILD_TESTS` | `ON`, `OFF` | `ON` | Сборка тестов |
| `FC_BUILD_VISUALIZER` | `ON`, `OFF` | `OFF` | Сборка визуализатора |

## Использование

```cpp
fc::FileCollector collector;
collector.CollectFile(1, 10);

collector.OnNewChunk(1, 0, {'A', 'B', 'C', 'D'});
collector.OnNewChunk(1, 2, {'C', 'D', 'E', 'F'});
collector.OnNewChunk(1, 6, {'G', 'H', 'I', 'J'});

std::optional<fc::OwnedFile> file = collector.TakeFile(1);  // ABCDEFGHIJ
```

| Метод | Описание |
|---|---|
| `CollectFile(id, size)` | Регистрирует файл. Повторный вызов с тем же размером игнорируется, с другим размером приводит к `std::invalid_argument`. |
| `OnNewChunk(id, pos, chunk)` | Добавляет чанк и возвращает `ChunkStatus`: `Accepted`, `Duplicate`, `UnknownFile` или `OutOfRange`. |
| `TakeFile(id)` | Возвращает собранный файл с передачей владения буфером, без копирования. Файл удаляется из коллектора. |
| `WaitAndTakeFile(id, timeout)` | Аналог `TakeFile` с ожиданием завершения сборки. |
| `ReadAvailable(id, pos, reader)` | Чтение без копирования: колбэк получает непрерывный готовый участок, начиная с `pos`. |
| `ReadRange(id, pos, len, reader)` | Чтение без копирования: колбэк вызывается для каждого готового участка в диапазоне. |
| `CopyAvailable(id, pos, out)` | Копирует готовый участок, начиная с `pos`, в буфер вызывающего. |
| `ReadyBytes(id)`, `ReadyBytes(id, pos, len)` | Количество полученных байт в файле или в диапазоне. |
| `CancelFile(id)` | Удаляет файл из коллектора без завершения сборки. |

Отличия от исходного интерфейса:

- `OnNewChunk` возвращает статус вместо `void`. Некорректный или повторный чанк является штатной ситуацией при сетевой передаче, поэтому сообщается через возвращаемое значение, а не через исключение.
- Вместо `GetFile` предусмотрены два способа доступа: передача владения собранным файлом и чтение частично собранного файла через колбэк.

Обе реализации трекера доступны напрямую: `fc::BasicFileCollector<fc::IntervalTracker>` и `fc::BasicFileCollector<fc::BitmapTracker>`.

## Архитектура

### Хранение данных

Размер файла известен заранее, поэтому буфер выделяется целиком при регистрации, и каждый чанк копируется сразу на своё место. Каждый байт копируется ровно один раз, собранный файл находится в одном непрерывном буфере. Буфер не инициализируется нулями, так как любой байт перезаписывается до того, как становится доступен для чтения.

### Учёт полученных данных

Полученные диапазоны отслеживает трекер. Реализовано два трекера с общим интерфейсом (концепт `CoverageTracker`):

| | `IntervalTracker` | `BitmapTracker` |
|---|---|---|
| Структура | `std::map` непересекающихся интервалов | Бит на каждый байт файла |
| Вставка | O(log n) амортизированно | O(len / 64) |
| Память | O(число разрывов) | `size / 8` |
| Подходит для | Крупных чанков, приходящих примерно по порядку | Мелких чанков в случайном порядке |

Пример слабого места интервалов: однобайтовые чанки через один в файле размером 2 КБ дают тысячу узлов `std::map`, тогда как битовая маска для того же файла занимает 256 байт.

При вставке трекер возвращает только ранее не полученные части чанка, поэтому пересекающиеся участки и дубликаты повторно не копируются.

### Синхронизация

- Таблица файлов защищена `std::shared_mutex` и блокируется только на время поиска.
- Каждый файл содержит два трекера: `claimed` (байты, запись которых уже начата) и `ready` (записанные байты, доступные для чтения). Запись чанка выполняется в три этапа: резервирование новых участков в `claimed` под мьютексом файла, копирование без блокировки, отметка в `ready` под мьютексом файла. Зарезервированные участки разных потоков не пересекаются, поэтому копирование выполняется параллельно и без гонок данных.
- Время жизни буфера защищено отдельным `std::shared_mutex`: читатели захватывают его в разделяемом режиме, `TakeFile` в эксклюзивном. Чтение не блокирует запись и только откладывает передачу владения.

Байты из `ready` больше не изменяются, поэтому после проверки их можно читать без блокировки. Файл считается собранным, когда все байты отмечены в `ready`, то есть после завершения всех копирований, поэтому на момент `TakeFile` запись в буфер не ведётся.

### Интерфейс чтения

`std::span`, возвращённый из метода, не защищён от освобождения буфера другим потоком через `TakeFile`. Объект, удерживающий блокировку за пределами класса, создаёт риск взаимной блокировки и неконтролируемого времени удержания. Колбэк удерживает блокировку строго на время чтения. Вызов `TakeFile` для того же файла внутри колбэка не допускается.

Собранный файл передаётся как `std::unique_ptr<uint8_t[]>` (обёртка `OwnedFile`), а не `std::vector`, поскольку конструктор `std::vector` инициализирует память нулями.

## Тестирование

| Файл | Содержание |
|---|---|
| `tracker_test.cpp` | Обе реализации трекера (typed tests), сверка с эталонной моделью на `std::vector<bool>` на случайных данных |
| `collector_test.cpp` | Однопоточные сценарии, все статусы `ChunkStatus`, граничные случаи |
| `collector_mt_test.cpp` | Параллельная запись в один и в разные файлы, чтение во время записи, конкурентный `TakeFile`, `TakeFile` во время чтения, отмена во время записи |
| `transfer_test.cpp` | Логика визуализатора без UI: разбиение на чанки, загрузка файла, конфигурация, многопоточная передача с остановкой, уничтожением и параллельным чтением |

Многопоточные тесты рассчитаны на запуск под санитайзерами:

```bash
cmake -S . -B build-tsan -DFC_SANITIZER=thread
cmake --build build-tsan -j
ctest --test-dir build-tsan
```

Все тесты проходят под ThreadSanitizer и под AddressSanitizer с UBSan. Работоспособность проверок подтверждена: удаление `claimed` обнаруживается ThreadSanitizer, внесённая утечка обнаруживается LeakSanitizer. На macOS LeakSanitizer недоступен, для поиска утечек используется `leaks --atExit -- ./build/tests/file_collector_tests`.

## TODO/Проблемы

- Реализовать автоматический выбор коллектора
- Чанки, полученные до вызова `CollectFile`, отбрасываются. Если данные могут опережать метаданные, требуется буферизация ранних чанков.
- В режиме `bitmap` маска хранится в двух экземплярах (`claimed` и `ready`).
- Таблица файлов общая для всего коллектора; при большом числе файлов её можно разделить на шарды.
- `std::shared_mutex` не гарантирует справедливость: при непрерывном потоке читателей `TakeFile` может ожидать длительное время.
